# SakuNet 性能与稳定性实测（v1.0）

## 先说清测的是什么

用户问得最多的三个问题：**网速会不会被软件拖慢、稳不稳、安全不安全**。这一轮用实测数回答前两个（安全面见 [SECURITY.md](../SECURITY.md)），方法一句话：**全部测试在本机回环（loopback）上做，不出公网**。

为什么不测公网速度：公网测速测到的是**线路**（节点带宽、运营商、跨境质量），不是软件。同一个节点用 v2rayN 测和用 SakuNet 测，公网数字的差异基本来自线路波动，说明不了软件问题。软件能决定的只有一件事：**它自己在转发路径上加了多少开销**。回环把线路变量清零，剩下的差异就是软件本身的账。

> 关于「Clash Verge 比 v2rayN 慢」这类说法：两个客户端的内核不同（mihomo vs xray/sing-box 系），在回环极限吞吐下确实能测出内核间个位数到两位数百分比的差距；但日常公网使用里瓶颈几乎永远是线路而非内核。下面 SakuNet 的数也是同样性质：看**相对开销**，不要拿回环的绝对 Gbps 去套公网体验。

## 测试环境

- 本机：Linux VM，4 vCPU 可见 / 内存 7.9 GB（与其他工作负载共享，数字含共租噪声，结论只取相对值）
- 内核：sing-box 1.14.4（与发布包同版本）
- 目标服务器：本地 Go HTTP/HTTPS 服务（127.0.0.1:18808/18809，流式吐数不落盘），直连实测 29 Gbps，排除目标端瓶颈
- 演示配置：测试 Surge 配置（1 个假节点 192.0.2.30、Main 组默认 DIRECT、FINAL→Main、MITM 名单仅 mitm.example、1 条重写规则、测试 CA）；目标主机为 127.0.0.1，**不在 MITM 名单内，走透传路径**（与真实使用中绝大多数 HTTPS 流量的路径相同）
- 场景一「裸内核」：sing-box 单独运行，mixed 入站 → direct 出站（与 SakuNet 生成配置同款 sniff 规则）
- 场景二「全栈」：客户端 → SakuNet MITM 层（:2081）→ sing-box（:2080）→ 目标，即发布版的真实链路（SakuNet 本体进程同时承载面板与 MITM 层）

## A. 转发开销对照结果

大文件吞吐：512 MiB/次 × 5 次（HTTP 全栈另加测 5 次），取中位。

| 路径 | 裸内核 | 全栈（经 MITM 层） | 差 |
|---|---|---|---|
| HTTPS（CONNECT 隧道） | 3,967 Mbps | 3,933 Mbps | **−0.9%** |
| 明文 HTTP（代理 GET） | 8,681 Mbps | ≈5,743 Mbps（两批 10 次中位） | **−34%** |

小请求延迟：每请求新建连接，n=120，0 错误。

| 路径 | 直连（参考）p50 / p95 | 裸内核 p50 / p95 | 全栈 p50 / p95 | 全栈比裸内核 p50 增量 |
|---|---|---|---|---|
| HTTPS | 3.180 / 4.106 ms | 4.069 / 5.451 ms | 5.317 / 17.598 ms | **+1.25 ms** |
| 明文 HTTP | 0.287 / 0.603 ms | 0.865 / 1.494 ms | 1.654 / 3.145 ms | **+0.79 ms** |

注：全栈 HTTPS 延迟 p95（17.6 ms）受共享 VM 噪声污染明显（同批 max 28 ms），p50 更能代表常态；两组延迟的增量都在 1 ms 量级。

进程开销（吞吐测试窗口内采样）：

| | CPU（合计） | 峰值内存 |
|---|---|---|
| 裸内核（sing-box 单进程） | 4.00 s（窗口 8.0 s，≈单核 50%） | 58.8 MiB |
| 全栈（SakuNet + sing-box） | 6.02 s（窗口 9.7 s，≈单核 62%）：SakuNet 2.88 s + sing-box 3.14 s | SakuNet 11.9 MiB + sing-box 59.9 MiB ≈ 71.8 MiB |

**一句话结论：全栈相对裸内核，HTTPS 隧道吞吐开销约 1%（噪声级）；明文 HTTP 路径在回环极限速率下慢约三分之一；每请求延迟多约 1 ms；SakuNet 本体进程内存仅约 12 MiB。**

明文 HTTP 为什么慢，代码里有实据：MITM 层的明文路径（`internal/mitm/mitm.go` 的 `handlePlainHTTP`）为**每个请求新建一个 http.Transport** 并向上游发起完整往返，没有连接复用；而 CONNECT 隧道路径是原始字节拼接（splice），所以几乎零损耗。优化方向明确（Transport 提升为服务端级 + 开启上游 keep-alive），但要强调：这个差距只在**回环数 Gbps 极限**下才有体感——真实公网明文 HTTP 流量既少、速率又远低于这个量级（≤百 Mbps 级），此时该路径的开销占比可忽略。它列入后续优化清单，不构成发布阻断项。

## B. 稳定性压测（25 分钟混合负载）

方法：全栈链路（经 2081，HTTPS），负载发生器循环执行「48 MiB 大文件下载 + 40 次小请求」，全程统计错误；每 10 秒采样两进程 RSS；每 60 秒轮询 /api/status 核对内核 PID 与运行状态（PID 变化即视为重启）。

结果（全程经 MITM 层 2081 → sing-box，HTTPS）：

| 指标 | 实测 |
|---|---|
| 时长 | 25 分钟（1500 s） |
| 负载总量 | 4,618 轮 ×（48 MiB 下载 + 40 小请求）＝ **216.5 GiB 下载 + 184,720 次小请求** |
| 错误数 | **0**（大文件全部完整校验长度、小请求全部 200） |
| 内核重启/崩溃 | **无**：每 60 秒轮询 /api/status 共 26 次，PID 恒为 11661、状态恒为 running |
| SakuNet 本体内存 | 起 11.2 MiB → 前半均值 9.1 → 后半均值 8.3 → 止 7.4 MiB（峰值 11.6） |
| sing-box 内存 | 起 60.5 MiB（承接 A 组后的热态峰值）→ 前半均值 17.4 → 后半均值 16.9 → 止 15.6 MiB |

判读：两进程内存都是**先回落、后走平**的形态（Go 运行时在 A 组峰值后把空闲堆归还系统，随后稳态维持）——前后半程均值差在 1 MiB 级、终值低于初值，**无持续增长、无泄漏迹象**；216 GiB 量级流量零错误、内核零重启。压测期间速率随共享 VM 的 CPU 配额有波动（各进程被限在约单核 30–40%），属环境限流、与软件无关，错误计数不受影响。

短时压测只能证伪明显的泄漏与崩溃；更长时（数天级）的常驻表现需真实使用观察，面板自检与诊断包即为此备的通道（见 README）。

## 附带发现（本轮实测撞到的真问题）

导入的 Surge 配置若以 `FINAL,DIRECT` 结尾，生成的 sing-box 配置里远程 DNS 的 detour 会指向 direct 出站，sing-box 1.14.4 在 **run 时** FATAL 退出（`detour to an empty direct outbound makes no sense`），而 `sing-box check` 不拦——表现为面板点启动后内核随即退出。FINAL 指向策略组（如 FINAL,Main）的配置不受影响。本轮 bench 配置已按 FINAL,Main 绕开；此问题应单独修（生成配置时 FINAL 为 DIRECT 则让 dns-remote 直连或换 detour），在此登记待修。

## 复现方法

测试工具（目标服务器/客户端/采样器）为一次性 bench 程序：目标服务器流式生成数据、客户端做吞吐与延迟统计、采样器读 /proc/<pid>/stat 与 VmRSS。场景切换只改客户端的代理入口（2080 或 2081），其余条件不动。
